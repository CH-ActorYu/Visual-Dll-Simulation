## 1. 产品定位

本项目是一款视觉相关的桌面软件。核心诉求：

> **每项业务功能都是一个独立模块（独立 DLL / 独立项目），可以从软件中单独拆出来，给到别的项目直接引用使用。**

两个关键概念（判定细则见 §4.5）：

- **业务功能**：输出带业务结论的完整场景（如"测距"输出 mm），单独成模块 DLL；
- **基础能力**：采集、预处理、找目标、跟踪等通用算子，不单独成模块，统一沉淀在共享基础层（Abstractions / IO / VisionBase），被各业务模块复用。

因此交付物分两层：

| 层 | 交付物 | 使用者 |
| --- | --- | --- |
| 软件层 | `Visual.App`（WPF 可执行程序）：完整的操作界面，加载各功能模块 | 直接操作软件的人 |
| 模块层 | `Visual.<功能>.dll`（如 `Visual.Distance.dll`）：纯算法/业务类库，**不依赖 UI**，可被任意 .NET 项目引用 | 其他软件项目（首个消费者：HardwareModularWorkflow 硬件工作流平台） |

典型消费场景：HardwareModularWorkflow 引用测距 DLL 组，在其 `OpenCvCameraDriver`（`IHardwareDriver` 实现）内调用测距 API，把"实时测距"变成工作流中的一个硬件步骤——**模块 DLL 是被调用方，不感知宿主的存在**。

```
┌─────────────────────────────┐   ┌──────────────────────────────────┐
│ Visual.App (WPF 软件)        │   │ HardwareModularWorkflow          │
│  └─ 引用 → Visual.Distance  │   │  └─ OpenCvCameraDriver           │
│            .dll 组           │   │       └─ 引用 → 测距 DLL 组       │
└─────────────────────────────┘   └──────────────────────────────────┘
              同一组 DLL，两种消费方式
```

## 3. 需求约束（Constraints）

### 3.1 模块 DLL 约束（可拆性的根本保障）

| 编号 | 约束 |
| --- | --- |
| C-01 | 模块项目为纯类库（`net10.0`），**禁止引用 WPF/WinForms/任何 UI 框架** |
| C-02 | 模块对外只暴露：接口（如 `IDistanceService`）+ DTO（如 `DistanceMeasurement`）+ 工厂/构建入口；实现类 `internal` |
| C-03 | 模块依赖只允许：共享层 DLL + OpenCvSharp4（含 runtime.win）+ .NET BCL；不引入宿主专属框架（DI 容器、ORM 等） |
| C-04 | 模块不读写调用方的文件/配置系统；所需参数（标定值、阈值）全部由调用方经 API 传入，序列化格式（JSON）由模块定义 |
| C-05 | 模块内所有耗时操作提供异步 API（`Task` + `CancellationToken`）；不假设调用方的线程模型，内部线程自行管理 |
| C-06 | 模块抛出的异常收敛为模块自定义异常类型，不向调用方泄漏内部第三方异常 |
| C-07 | 模块带语义化版本号（如 `Visual.Distance 1.0.0`），公共 API 变更遵循 SemVer |
| C-08 | 每个模块配套**无 UI 的测试工程**（xUnit 控制台可跑），证明脱离软件可用 |

### 3.2 软件层约束

| 编号 | 约束 |
| --- | --- |
| C-09 | 软件分层：App（WPF UI）→ AppCore（交互/编排）→ 模块 DLL + 共享层 DLL；UI 不直接写算法 |
| C-10 | 技术栈：.NET 10 / WPF / CommunityToolkit.Mvvm / OpenCvSharp4；DI 用 Microsoft.Extensions.DependencyInjection |
| C-11 | 软件通过项目引用加载模块；模块同时以 DLL 形式构建输出（`dotnet build` 即可拿到可分发 DLL） |
| C-12 | 耗时操作全部异步，UI 线程不阻塞 |

### 3.3 范围约束（本期）

| 编号 | 约束 |
| --- | --- |
| C-13 | 本期业务功能仅**实时目标测距**一个模块；软件壳（视频源、圈选、叠加显示）为配套 |
| C-14 | 本期实现为单相机、单 ROI、单目标，但 **API/DTO 按多目标、多帧源兼容设计**（见 §5.5-A）；测距方案为单目 + 标定 |

│  │        #  几何换算工具（像素↔物理量、ROI 裁剪与越界收敛）
│  ├─ modules/                       # ===== 业务模块层（对外交付的 DLL）=====
│  │  └─ Visual.Distance/            # ★ 测距模块（本期唯一业务模块）

│  ├─ app/                           # ===== 软件层（不可拆、不对外）=====

### 4.1 依赖方向（单向、不可违反）

```
Visual.App / AppCore
   │  （可依赖下面全部）
   ▼
Visual.Distance  ──依赖──►  Visual.VisionBase  ──依赖──►  Visual.Abstractions
   │                             ▲                            ▲
   └────────依赖─────────────────┘                            │
Visual.IO  ────────────────依赖────────────────────────────────┘
```

- 箭头只允许向下；**业务模块之间禁止互相依赖**；
- 模块间如需协作（一个模块的输出作为另一个模块的输入），由 App 层组合，数据走 Abstractions 的通用类型；
- shared 三层不知道任何"业务"的存在；IO 不知道帧会被拿去干什么。

### 4.2 各层职责一句话

| 层 | DLL | 职责 | 独立交付？ |
| --- | --- | --- | --- |
| 基础契约 | Visual.Abstractions | 跨模块通用的值对象/结果基类/异常/模块入口形态 | 是（随模块一起走） |
| IO 采集 | Visual.IO | 只负责"稳定拿到带序号的帧"，设备差异在此屏蔽 | 是（可单独给仅需取帧的项目） |
| 视觉基础 | Visual.VisionBase | 预处理/分析算子（含灰度、缺陷类基础算子）、检测跟踪基类、几何换算——模块的"公共零件箱" | 是（随模块一起走） |
| 业务模块 | Visual.Distance | 组合公共零件完成一个完整业务功能 | **是（核心交付物）** |
| 软件层 | Visual.App / AppCore | 人机交互与模块编排 | 否（WPF 耦合） |

### 4.3 为什么这样细分（拆 DLL 的判断标准）

**拆 DLL 的唯一理由：存在"独立的消费边界"——即有调用方只想用这一层、且可能单独升级它。**

- **Abstractions 必须拆**：它是所有模块和宿主之间的"语言"，调用方只引用它就能定义自己的适配层；版本变化最慢。
- **IO 必须拆**：存在真实独立消费者——HardwareModularWorkflow 只需要"取帧"时（相机已由其硬件体系管理），可只引用 IO 而不碰测距。
- **VisionBase 必须拆**：它是未来所有业务模块的公共件；不拆则每个新模块复制一份预处理/跟踪代码。
- **Distance 必须拆**：本期核心诉求本身。

### 4.4 明确不再细分的部分（及原因）

| 候选拆分 | 结论 | 原因 |
| --- | --- | --- |
| 标定（Calibration）独立成 DLL | **不拆**，留在 Distance 模块内 | 单目标定公式与测距强耦合（同一组参数、同一次换算），当前无第二个消费者；独立出来只会多一次跨 DLL 传参。未来出现"多模块共用标定"再拆，届时从 Distance.Internal 平移即可 |
| 预处理 / 检测 / 跟踪 / 分析算子各自成 DLL | **不拆**，合并为 VisionBase 一个 DLL | 这些是同一管线的连续工序与算子集合，永远一起被模块引用；拆成多个 DLL 只增加部署和版本对齐成本，没有调用方会"只要跟踪不要检测" |
| 摄像头源 / 文件源各自成 DLL | **不拆**，同为 IO 内两个实现类 | 差异只是"帧从哪来"，由 `IFrameSource` 策略区分即可；按设备类型拆 DLL 会造成 IO 层数量爆炸 |
| 每个模块的 Contracts 单独成 DLL | **不拆**，Contracts 作为模块 DLL 内的文件夹 | 模块契约与模块同生命周期、同版本；单独成 DLL 会产生大量"1 个接口 1 个 DLL"的碎片，引用方反而要管理双倍依赖 |
| AppCore 的叠加渲染拆 DLL | **不拆** | 叠加渲染依赖 WPF 的 DrawingVisual/WriteableBitmap，离开 WPF 无意义，违反 C-01 |
| 按"实体/值对象/接口"分 DLL | **不拆** | 按代码种类分包没有消费边界支撑，只会得到互相依赖的 DLL 网 |

**原则总结：DLL 边界 = 消费边界 + 独立版本化需求；层内细分用命名空间/文件夹解决，不滥用程序集。**

### 4.5 基础 vs 业务的判定标准

拿到任何一项视觉能力，按下面四条判定。**四条全满足 → 归 VisionBase（基础）；任一不满足 → 归业务模块。**

| # | 判定问题 | 基础（VisionBase） | 业务（模块） |
| --- | --- | --- | --- |
| 1 | 输出含**业务结论**吗？（带单位/判定的结果：距离 mm、OK/NG、数量报表） | 不含，只输出图像/几何数据（掩膜、轮廓、坐标、相似度） | 含 |
| 2 | 持有**业务状态**吗？（标定参数、业务阈值、配方、会话） | 无状态，纯函数式"帧进→数据出" | 有状态 |
| 3 | 知道"**目标是什么**"吗？（类别语义、业务对象） | 不知道，只认像素与几何特征 | 知道（"这是零件 A"） |
| 4 | 换一个业务场景，**原样还有用**吗？ | 有用（任何场景都要灰度/找轮廓） | 没用，需要改参数语义或流程 |

一句话版：**"换个业务场景它还能原样复用吗？能 → 基础；不能/输出业务结论 → 业务。"**

#### 判定示例（争议项对照）

| 能力 | 归类 | 理由 |
| --- | --- | --- |
| 灰度、二值化、滤波、形态学、边缘 | 基础 | 纯像素变换，无业务语义（判定 1/4） |
| Blob/轮廓分析、模板匹配 | 基础 | 输出几何数据，不知道目标是什么（判定 3） |
| 缺陷类算子（污点/划痕/差异对比） | 基础 | 只输出"疑似异常区域+面积"，**不下 OK/NG 结论**（判定 1）；OK/NG 判定属业务 |
| "在 ROI 内找最显著目标并跟踪"（ITracker/TargetDetectorBase） | 基础 | 通用手段，测距和未来的计数等场景都能用（判定 4） |
| 标定 + 距离换算 | 业务 | 持有标定状态（判定 2），输出带单位的业务结论 mm（判定 1） |
| "识别目标是哪种零件/图形" | 业务 | 含类别语义，依赖具体对象库（判定 3） |
| "目标越界/停留超时"判断 | 业务 | 含业务规则与阈值（判定 1/2） |

#### 推论

- "计算之前的一切"（采集、预处理、找目标、跟踪）默认归基础层——它们不带业务结论；
- "识别"要拆开看：**找目标**（detection，几何层面）是基础；**认出是什么**（classification，语义层面）是业务；
- 一个业务模块 = 基础算子的组合 + 业务状态 + 业务结论。Distance 即是如此：VisionBase 找目标 → 模块内标定状态 → 输出 mm。

后续新业务功能 = `modules/` 下新增 `Visual.<功能>/`（依赖 shared 三层）+ App 内挂菜单，结构不变。

### 5.1 FR-01 测距模块（Visual.Distance）

**对外 API（Contracts）——调用方视角：**

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-01-01 | 提供服务接口：`IDistanceService`，方法含 `SetCalibration(...)` / `MeasureAsync(frame, rois, ct)`（**支持一次传多个 ROI**，多目标兼容设计）/ 配置读写（JSON 字符串导入导出） | P0 |

| FR-01-04 | 未标定调用测距 → 抛模块自定义异常（`NotCalibratedException`），不返回假数据 | P0 |
| FR-01-05 | 内部识别算法（轮廓/模板/颜色其一）可替换，但不改变 Contracts | P1 |
| FR-01-06 | 提供实时模式：订阅式连续测量（`IObservable<IReadOnlyList<DistanceMeasurement>>` 或事件），供 UI 实时刷新 | P0 |

**内部实现（模块开发者视角）：**

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-01-07 | ROI 内目标识别：输出目标框、中心点、像素尺寸、置信度；相邻帧跟踪 | P0 |
| FR-01-08 | 单目标定换算：参照物真实尺寸 + 像素尺寸 + 拍摄距离 → 换算参数；逐帧换算距离 | P0 |
| FR-01-09 | 连续 N 帧未检出时置信度降 0、距离置 null，不误报 | P1 |

| FR-03-02 | 鼠标圈选/清除 ROI（面积 < 16×16 拒绝并提示），越界自动收敛 | P0 |

| FR-03-04 | 实时叠加显示：目标框、中心点、距离文本；状态栏：未启动/未标定/未检出/测量中 | P0 |
| FR-03-05 | 菜单式功能入口：当前仅"测距"；后续业务模块按挂载方式出现 | P1 |

### 5.4 FR-04 可拆性验证（本期关键差异化需求）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-04-01 | 提供 ConsoleDemo：仅引用模块及共享层 DLL，无 UI 完成"VideoFileSource 取帧 → 给定 ROI → 输出距离" | P0 |
| FR-04-02 | 提供模块单元测试：图片样本 + 已知标定，断言测距结果，全程不启动 WPF | P0 |
| FR-04-03 | 输出分发说明：模块 + 共享层 DLL 清单（Distance/VisionBase/IO/Abstractions）+ OpenCvSharp 依赖 + 最小调用代码片段 | P0 |

### 5.5 边界与预留

#### A. 设计预留，本期不实现（避免将来破坏性变更）

| 编号 | 内容 | 预留方式 |
| --- | --- | --- |
| F-01 | 多目标 | API 现即支持一次传入多个 ROI、返回结果集合；DTO 带 `TargetId`。本期 UI 只提供单 ROI 圈选 |
| F-02 | 多相机/多帧源 | DTO 带 `SourceId`；服务不假设全局只有一路帧。本期 UI 只接一路 |
| F-03 | DNN/ONNX 识别增强 | 识别是测距模块的内部工序，替换实现不改 Contracts |
| F-04 | NuGet 私有源发布 | 本期以 DLL 直拷/项目引用分发 |

#### B. 明确不做（从规划移除，而非"暂缓"）

| 内容 | 移除原因 |
| --- | --- |
| "识别"作为独立业务模块 | 找目标是通用算子（已沉淀在 VisionBase），单独成为业务模块没有独立消费者；外部要"识别结果"时取 `DistanceMeasurement` 中的目标框/中心点即可。若未来出现"认出目标是什么"（分类语义）的真实需求，再按 §4.5 判定立项 |
| 缺陷检测、路径分析等**独立业务功能模块** | 与测距核心业务无关、无明确消费者；将来真有需要时按新需求单独立项，不在本文档挂账。注意：移除的是"业务模块立项"，其**基础算子**（灰度、二值化、Blob、污点/划痕检测等）作为公共能力沉淀在 VisionBase（见 FR-02），不属于被移除范围 |

## 6. 输入（Inputs）

### 6.1 模块 DLL 输入（API 级）

| 输入 | 类型 | 约束 |
| --- | --- | --- |
| 视频帧 | `Mat`（BGR）或 `FramePacket` | 非空、未释放 |
| ROI | 矩形集合（像素） | 调用方可传多个，每个 ROI 对应结果中一个 `TargetId`；由调用方保证在画面内，面积过小对应条目返回未检出 |
| 标定参数 | `CalibrationInfo`（参照物真实尺寸、像素尺寸、拍摄距离、单位） | 数值 > 0，否则参数校验异常 |
| 配置 | JSON 字符串 | 模块定义 schema，含标定与阈值 |

### 6.2 软件输入（用户级）

| 输入 | 约束/校验 |
| --- | --- |
| 摄像头选择 / 视频文件路径 | 打开失败明确提示，不崩溃 |
| ROI 圈选 | < 16×16 拒绝；越界收敛 |
| 标定表单 | 数值 > 0 校验，非法拒绝保存 |

### 6.3 外部项目调用输入

最小调用序列：`new DistanceServiceBuilder().Build()` → `SetCalibration(...)` → 逐帧 `MeasureAsync(frame, rois)` → 读 `IReadOnlyList<DistanceMeasurement>`。

## 7. 输出（Outputs）

### 7.1 模块 DLL 输出（API 级）

`MeasureAsync` 返回 `IReadOnlyList<DistanceMeasurement>`（每个传入 ROI 一条），单条结构：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| TargetId | string | 目标标识（与传入 ROI 对应） |
| SourceId | string? | 帧源标识（多相机预留，单源时为 null） |
| Distance | double? | 距离值；未检出/未标定为 null |
| Unit | string | mm / cm / m |
| Confidence | double | 0~1 |
| TargetCenter | Point? | 目标中心（像素） |
| TargetPixelSize | double? | 目标像素尺寸 |
| Timestamp | DateTime | 测量时间 |

实时模式：事件/流式推送同一集合结构。

### 7.2 软件输出（用户级）

- 实时画面叠加：目标框（绿）/未检出（灰）、距离文本（值+单位）
- 状态栏：未启动 / 未标定 / 未检出 / 测量中（当前距离）
- 标定参数本地持久化（JSON）

### 7.3 分发输出

按消费粒度分发（每组含版本号 + 依赖说明 + ConsoleDemo 源码）：

| 分发包 | 包含 DLL | 适用调用方 |
| --- | --- | --- |
| 完整测距包 | Distance + VisionBase + IO + Abstractions | 无相机体系的外部项目（默认） |
| 仅取帧包 | IO + Abstractions | 已有自己算法、只需要采集的项目 |
| 仅算法包 | Distance + VisionBase + Abstractions | 自带帧源的宿主（如 HardwareModularWorkflow，帧由其硬件体系提供） |

## 9. 验收标准（Acceptance Criteria）

### 9.1 验收场景

| 场景 | 前置条件 | 步骤 | 预期结果 |
| --- | --- | --- | --- |
| S1 软件闭环 | 接好摄像头 | 打开软件 → 圈选 ROI → 标定 → 观察 | 实时显示距离，移出目标显示未检出 |
| S2 测距精度 | 已标定 | 目标置于 3 个已知距离点（近/中/远），各测 10 次 | 平均误差 ≤ ±10%，单位正确 |
| S3 标定持久化 | 完成标定 | 重启软件 | 标定参数自动加载，无需重标 |
| **S4 DLL 独立可用** | 拿到完整测距包 DLL 组 | 新建控制台项目仅添加 DLL 引用，按最小调用序列跑视频文件 | 编译通过，逐帧输出距离，全程无 WPF/无软件安装 |
| S5 宿主集成 | HardwareModularWorkflow 引用 DLL 组 | 在其相机驱动中调用 `MeasureAsync`，工作流编排执行 | 距离作为步骤结果返回（`CommandResult.Data`） |
| S6 异常鲁棒 | — | 未标定测距 / 坏视频文件 / 采集中拔摄像头 | 自定义异常或明确状态提示，进程不崩溃 |
| S7 性能 | 720p 视频 | 连续 10 分钟 | ≥ 15 次/秒，UI 无卡顿 |
| S8 稳定性 | — | 连续运行 2 小时 | 无崩溃，内存增长 < 10% |

### 9.2 验收口径

- AC-M1：S1~S8 全部通过；
- AC-M2：**S4（DLL 独立可用）与 S5（宿主集成）是本项目的核心验收项**，证明"功能可拆分给别处直接使用"；
- AC-M3：精度满足 NFR-02（±10%）。

### 9.3 验收交付物

- Visual.App 可运行软件；
- 分发 DLL 组（按 §7.3）+ 依赖清单 + 最小调用示例；
- ConsoleDemo 与模块测试工程源码；
- 验收测试记录表（S1~S8 签认）。
